事务和数据一致性

事务用来保护一组相关操作：要么全部成功，要么全部失败。它是转账、下单、扣库存这类业务的安全底线。

一、为什么需要事务

转账场景

A 给 B 转 100 元，必须同时完成：A 扣 100，B 加 100。只成功一半，账就错了。

下单场景

创建订单、创建订单明细、扣库存通常要绑定在一起。订单创建了但库存没扣，也会出问题。

一句话：当一个业务动作需要多条 SQL 一起完成时，就要考虑事务。

二、事务的三个核心命令

命令作用怎么理解
START TRANSACTION开始事务从这里开始，后面的操作先放在一个事务里。
COMMIT提交事务确认所有操作都成功，把修改真正保存。
ROLLBACK回滚事务出现问题时撤销本次事务中的修改。

三、准备账户练习表

为了不影响前面的练习表，这里新建 transaction_accounts 表。

-- 创建一张专门练习事务的账户表
CREATE TABLE IF NOT EXISTS transaction_accounts (
  -- 账户 id
  id INT PRIMARY KEY AUTO_INCREMENT,
  -- 账户名称
  account_name VARCHAR(50) NOT NULL,
  -- 账户余额，不能小于 0
  balance DECIMAL(10, 2) NOT NULL CHECK (balance >= 0),
  -- 创建时间
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

四、准备账户数据

准备两个账户：A 账户有 1000 元，B 账户有 500 元。

-- 插入两条账户数据
INSERT INTO transaction_accounts (account_name, balance) VALUES
  ('A 账户', 1000.00),
  ('B 账户', 500.00);

先查看账户余额，确认初始数据。

-- 查看账户余额
SELECT id, account_name, balance
FROM transaction_accounts;

五、没有事务时的问题

下面两条 SQL 表示：A 账户扣 100，B 账户加 100。如果第一条成功，第二条失败，钱就不一致了。

-- 没有事务保护：如果中间失败，可能只成功一半
UPDATE transaction_accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE transaction_accounts
SET balance = balance + 100
WHERE id = 2;
学习重点：不是这两条 SQL 本身复杂，而是它们必须作为一个整体成功或失败。

六、用事务完成转账

事务会把两次余额修改包起来。都成功就提交；如果发现问题，就回滚。

-- 开始事务：从这里开始把多条 SQL 当成一个整体
START TRANSACTION;

-- A 账户扣 100
UPDATE transaction_accounts
SET balance = balance - 100
WHERE id = 1;

-- B 账户加 100
UPDATE transaction_accounts
SET balance = balance + 100
WHERE id = 2;

-- 确认两步都没问题后，提交事务
COMMIT;

提交后再查询余额，确认转账结果。

-- 查看事务提交后的账户余额
SELECT id, account_name, balance
FROM transaction_accounts;

七、用 ROLLBACK 撤销事务

下面这段适合单独复制执行。执行到查询时，你能看到事务内的临时变化；执行 ROLLBACK 后，本次修改会撤销。

-- 开始事务，准备演示回滚
START TRANSACTION;

-- 先让 A 账户扣 200
UPDATE transaction_accounts
SET balance = balance - 200
WHERE id = 1;

-- 在事务中查看余额，可能能看到临时变化
SELECT id, account_name, balance
FROM transaction_accounts;

-- 回滚事务：撤销 START TRANSACTION 之后的修改
ROLLBACK;

-- 再次查看余额，确认刚才的扣款已经撤销
SELECT id, account_name, balance
FROM transaction_accounts;

八、事务的 ACID 先了解

特性中文理解例子
Atomicity 原子性要么全成功，要么全失败转账不能只扣不加
Consistency 一致性事务前后数据规则仍然成立余额不能变成不合理状态
Isolation 隔离性多个事务互相不要乱影响多人同时下单时库存不能乱
Durability 持久性提交后的数据要保存下来COMMIT 后断电也不应该丢数据
入门阶段：先重点理解“原子性”。隔离级别、锁、并发问题后面再深入。

九、哪些场景需要事务

场景为什么需要事务
转账一个账户扣钱，另一个账户加钱，必须一起成功。
下单创建订单、创建明细、扣库存，通常要绑定在一起。
分配角色批量插入用户角色关系时，失败后可能要整体撤销。
删除复杂业务数据删除主数据和关联数据时，要避免只删一部分。

十、哪些场景通常不需要事务

普通查询

单纯 SELECT 列表、详情、统计，通常不需要你手动开启事务。

单条简单修改

单条 UPDATE 或 INSERT 在 MySQL 中通常会自动作为一个小事务提交。

简单判断：如果一个业务动作包含多条必须一起成功的写操作，就优先想到事务。

十一、后端里事务长什么样

后端代码里，事务通常不是手写 START TRANSACTION，而是由 ORM 或数据库工具提供事务方法。

-- 后端事务的核心思想仍然是这三步
START TRANSACTION;

-- 执行业务相关的多条 SQL
-- 例如：创建订单、创建订单明细、扣库存

COMMIT;

-- 如果中途出错，就执行 ROLLBACK
全栈视角：你以后用 Node.js、NestJS、Prisma 或 TypeORM 时，事务思想是一样的，只是写法会变成框架 API。
