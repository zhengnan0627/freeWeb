索引和查询性能

索引是数据库性能里最重要的基础能力之一。它能让查询更快，但也会让写入和维护变重，所以不是越多越好。

一、索引是什么

像书的目录

没有目录时，只能一页一页找；有目录时，可以先定位大概位置，再快速找到内容。

像 Excel 的快速定位

没有索引时，数据库可能要从第一行扫到最后一行；有合适索引时，可以更快定位符合条件的数据。

重点：索引主要服务于查询条件、排序、关联字段，不是给每个字段都加。

二、先创建一张索引练习表

为了不影响前面的 users 表，这里使用 index_users 作为练习表。

-- 创建一张专门练习索引的用户表
CREATE TABLE IF NOT EXISTS index_users (
  -- 主键本身就是一种索引
  id INT PRIMARY KEY AUTO_INCREMENT,
  -- 用户名
  username VARCHAR(50) NOT NULL,
  -- 邮箱
  email VARCHAR(100),
  -- 手机号
  phone VARCHAR(20),
  -- 年龄
  age INT,
  -- 状态
  status VARCHAR(20) DEFAULT 'active',
  -- 创建时间
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

三、准备练习数据

插入几条不同数据，方便观察按邮箱、状态、时间查询的场景。

-- 插入几条索引练习数据
INSERT INTO index_users (username, email, phone, age, status) VALUES
  ('zhangsan', 'zhangsan@example.com', '13800000001', 18, 'active'),
  ('lisi', 'lisi@example.com', '13800000002', 22, 'active'),
  ('wangwu', 'wangwu@example.com', '13800000003', 30, 'disabled'),
  ('zhaoliu', 'zhaoliu@example.com', '13800000004', 25, 'active'),
  ('xiaoming', 'xiaoming@example.com', '13800000005', 19, 'disabled');

四、主键索引

PRIMARY KEY 会自动创建索引，所以按 id 查询通常很快。

-- 根据主键 id 查询单个用户
SELECT id, username, email, status
FROM index_users
WHERE id = 1;
真实项目：详情、编辑、删除通常都按 id 定位，这也是主键索引非常重要的原因。

五、普通索引

如果经常按 status 查询用户列表，可以给 status 创建普通索引。

-- 给 status 字段创建普通索引
CREATE INDEX idx_index_users_status
ON index_users (status);

创建索引后，下面这类查询可能更容易用到索引。

-- 查询 active 状态的用户
SELECT id, username, status
FROM index_users
WHERE status = 'active';

六、唯一索引

唯一索引既能加速查询，又能保证字段不重复。邮箱、手机号、账号常见这种设计。

-- 给 email 字段创建唯一索引，保证邮箱不能重复
CREATE UNIQUE INDEX uk_index_users_email
ON index_users (email);

下面这句如果邮箱已经存在，会因为唯一索引而报错。

-- 观察唯一索引：重复邮箱会报错，建议单独执行
INSERT INTO index_users (username, email, phone, age)
VALUES ('repeat_email_user', 'zhangsan@example.com', '13800000999', 28);

七、联合索引

如果经常按状态筛选，并按创建时间排序，可以考虑联合索引。

-- 创建 status 和 created_at 的联合索引
CREATE INDEX idx_index_users_status_created_at
ON index_users (status, created_at);

这个索引更适合下面这种查询：先按 status 筛选，再按 created_at 排序。

-- 查询 active 用户，并按创建时间倒序
SELECT id, username, status, created_at
FROM index_users
WHERE status = 'active'
ORDER BY created_at DESC;
顺序很重要：联合索引 (status, created_at) 不等于 (created_at, status)。常见做法是把更常用于筛选的字段放前面。

八、索引不是越多越好

好处代价
让某些查询更快插入、修改、删除时要维护索引，写入会变慢
能帮助排序和关联索引会占用额外磁盘空间
唯一索引能防重复索引太多会增加数据库维护成本
入门原则：经常用于 WHERE、JOIN ON、ORDER BY 的字段，才值得优先考虑索引。

九、哪些写法可能让索引不好用

对字段做函数处理

如果对索引字段做函数或计算，数据库可能没法直接利用索引。

-- 不推荐：对字段做函数处理，可能影响索引使用
SELECT id, username, created_at
FROM index_users
WHERE DATE(created_at) = '2026-06-11';

LIKE 前面有百分号

LIKE '%xiao%' 前面不固定，普通索引通常很难直接定位。

-- 可能不容易利用普通索引：前面有 %
SELECT id, username
FROM index_users
WHERE username LIKE '%xiao%';
先别焦虑：入门阶段先理解这些写法“可能影响索引”，不用立刻钻特别深的执行计划细节。

十、用 EXPLAIN 看查询计划

EXPLAIN 不会真正返回业务数据，它会告诉你数据库准备怎么执行这条查询。

-- 查看这条查询可能如何执行
EXPLAIN
SELECT id, username, status, created_at
FROM index_users
WHERE status = 'active'
ORDER BY created_at DESC;
字段先看什么
type访问方式，通常越接近 const、ref、range 越好；ALL 表示可能全表扫描。
possible_keys可能用到哪些索引。
key实际使用了哪个索引。
rows预估要扫描多少行。

十一、删除索引

如果索引建错了，或者确认不再需要，可以删除索引。

-- 删除 status 字段上的普通索引
DROP INDEX idx_index_users_status
ON index_users;
注意：删除索引会影响查询性能。真实项目中不要随便删线上索引，需要先确认影响范围。

十二、本阶段练习

能说出索引为什么像书的目录。
能区分主键索引、普通索引、唯一索引、联合索引。
能给经常查询的字段创建普通索引。
能解释为什么邮箱适合唯一索引。
能理解联合索引字段顺序很重要。
能知道索引不是越多越好。
能用 EXPLAIN 初步查看查询有没有可能用到索引。
