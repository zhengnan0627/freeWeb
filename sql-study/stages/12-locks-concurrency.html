锁和并发控制

事务解决的是“一组操作要么都成功，要么都失败”；锁解决的是“多人同时改同一份数据时，别互相踩坏”。

一、为什么需要锁

转账会撞车

如果两个人同时修改同一个账户余额，都先读到旧值，再分别写回去，就可能把其中一次修改覆盖掉。

库存会超卖

库存只剩 1 件时，两个人同时下单，如果都先看到库存大于 0，就可能都扣成功，结果卖出 2 件。

一句话：并发问题不是 SQL 写错，而是多个事务同时操作同一份数据时发生了竞争。

二、先准备库存练习表

这里用一张新的练习表 lock_products，避免影响前面的事务练习。

-- 创建一张专门练习并发和锁的商品表
CREATE TABLE IF NOT EXISTS lock_products (
  -- 商品 id
  id INT PRIMARY KEY AUTO_INCREMENT,
  -- 商品名称
  product_name VARCHAR(50) NOT NULL,
  -- 库存数量，不能小于 0
  stock INT NOT NULL CHECK (stock >= 0),
  -- 更新时间
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

三、准备库存数据

先准备一条库存只有 1 的商品，后面方便演示“超卖”问题。

-- 插入一条库存为 1 的商品数据
INSERT INTO lock_products (product_name, stock)
VALUES ('限量商品', 1);

先看当前库存。

-- 查看商品库存
SELECT id, product_name, stock
FROM lock_products;

四、没有锁时可能发生什么

下面是一个“看起来没问题，但并发下有风险”的思路：先查库存，再更新库存。

-- 没有显式加锁时的典型思路
SELECT id, product_name, stock
FROM lock_products
WHERE id = 1;

-- 如果代码层判断 stock > 0，就执行扣减
UPDATE lock_products
SET stock = stock - 1
WHERE id = 1;
风险点：两个事务可能同时执行第一条查询，都看到 stock = 1，然后都继续扣减，结果就超卖了。

五、行锁是什么

锁住一行

行锁的意思是：当前事务先占住某一行，其他事务想修改这行时，需要等当前事务结束。

不是锁整张表

数据库通常更希望锁得尽量小。只锁你真正要操作的那一行，其他行还能继续被别的事务正常处理。

六、SELECT ... FOR UPDATE

FOR UPDATE 常用于事务里，表示：我不只是看这条数据，我很快就要改它，请先把它锁住。

-- 开始事务，并把 id = 1 这行商品数据先锁住
START TRANSACTION;

SELECT id, product_name, stock
FROM lock_products
WHERE id = 1
FOR UPDATE;
理解方式：普通 SELECT 更像“看一眼”；SELECT ... FOR UPDATE 更像“看一眼并先把位置占住，因为我马上要改”。

七、用锁保护扣库存

下面是一段更安全的库存扣减思路：先开启事务，再用 FOR UPDATE 锁住商品行，确认库存足够后再扣减，最后提交。

-- 开始事务，准备扣库存
START TRANSACTION;

-- 先锁住要操作的商品行
SELECT id, product_name, stock
FROM lock_products
WHERE id = 1
FOR UPDATE;

-- 确认库存足够后，再执行扣减
UPDATE lock_products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;

-- 扣减成功后提交事务
COMMIT;
现实里的完整做法：后端通常还会检查 UPDATE 影响了几行。如果影响行数是 0，就说明库存不足或被别人先抢走了。

八、锁是怎么表现出来的

如果事务 A 先用 FOR UPDATE 锁住了 id = 1 的商品，事务 B 再来修改这行时，通常会等待事务 A 提交或回滚。

-- 事务 A：先锁住商品行
START TRANSACTION;

SELECT id, product_name, stock
FROM lock_products
WHERE id = 1
FOR UPDATE;

-- 事务 B：这时如果也想更新同一行，通常会等待
UPDATE lock_products
SET stock = stock - 1
WHERE id = 1;
你在 Navicat 里怎么观察：要真正看到“等待”的效果，通常需要两个独立查询窗口或两个连接同时操作。

九、锁和事务的关系

概念解决什么问题
事务保证一组操作要么都成功，要么都失败。
锁保证多人同时改同一份数据时，不会互相覆盖或产生脏结果。
搭配理解：事务偏“整体成功失败”，锁偏“并发时谁先改、谁后改”。

十、悲观锁和乐观锁先建立感觉

悲观锁

先假设冲突很可能发生，所以先锁住数据再改。SELECT ... FOR UPDATE 就是典型例子。

乐观锁

先假设冲突不常发生，不先锁，而是在更新时检查版本号或更新时间，发现被别人改过就重试或报错。

乐观锁在后端代码里很常见，通常会多一个版本字段。

-- 乐观锁思路：只有版本号没变，才允许更新
UPDATE some_table
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
  AND version = 3;
入门建议：现在先把悲观锁和 FOR UPDATE 理解透，乐观锁先知道思路就够了。

十一、哪些场景要特别想到锁

场景为什么会有并发冲突
扣库存多人同时下单，都会盯着同一件商品的库存。
抢优惠券同一批券被很多人同时领取。
余额扣减多人或多个请求同时修改同一个账户余额。
座位/名额预约有限资源被多人同时争抢。

能解释为什么先查库存再更新，在并发下可能超卖。
能理解 SELECT ... FOR UPDATE 为什么要放在事务里使用。
能说出行锁为什么比锁整张表更常见。
能区分悲观锁和乐观锁的大致思路。
能判断库存、余额、抢券这类场景为什么要考虑并发控制。
